## 0. 요약

P1 페르소나를 Swarm(gpt-6.1-terra)으로 12/1~1/31 끝까지 두 번 돌렸다. **이해와 안전은 잘한다. 약한 것은 목표 달성 기여와 비용**이다. 약한 원인은 대부분 모델 능력이 아니다. 하네스가 에이전트에게 **주지 않는 정보**, 그리고 **코드가 해야 할 일을 LLM이 하고 있는 것**이 원인이다.

| 구분 | 잘된 것 | 부족한 것 |
|---|---|---|
| 이해 | 쟁점 재현율 0.925 (37/40), 숨은 사실을 겨냥한 질문 20/23 | 정답과 안 맞는 쟁점 64개 |
| 안전 | 보호 지출 침해 0건, 지어낸 숫자는 검증에서 차단 | |
| 목표 기여 | 제안 수락 4 · 보류 2 · 거절 0 | 처음 두 주 제안 0개, 절약 기댓값 97,171원 (필요 월 저축 24만 원 대비 작음), 끝난 쟁점 해결 처리 0/1 |
| 비용 | 입력 토큰 338만 → 134만 (PR #19) | 여전히 실행 1회에 134만 토큰 |

개선은 크게 네 묶음이다.

1. **정확도:** 월 저축액 추정, 부족분 미확인 처리, 가입 주는 분석만 하기
2. **기억과 추적:** 수락 후 성과 추적, 같은 제안 쿨다운, 프로필에 출처·상태·만료 붙이기
3. **입력 준비 (LLM 전에 코드가):** 코드 쟁점 탐지, 원본 거래는 필요한 만큼만, 규칙 게이트
4. **사용자 이해:** 온보딩 질문을 에이전트 행동과 연결, "AI가 이해한 나" 화면, 전략 유형 선호, 표현 규칙

원칙은 그대로 둔다. **LLM은 판단과 설명을, 코드는 숫자와 검증을 맡고, 결정은 사용자가 한다.**

## 2. P1 실행에서 찾은 문제

결과 파일: `eval/runs/baseline_P1_swarm_gpt-6.1-terra_261127-154606.json`(개선 전), `..._261127-165743.json`(개선 후). git에는 올라가지 않는다.

### 2.1 처음 두 주 제안 0개

12/1(가입)과 12/6(첫 주간)의 바통 기록은 같은 순서로 막혔다.

```
strategist: 소리랑·무비온 해지 제안 (월 21,400원)
→ reviewer: 부족분 = 필요 월 저축 240,000 − 지금 월 저축(모름) → 계산 불가
   → 숫자를 지어낼 수 없어 check_gap_coverage 를 부르지 않음
   → 코드 규칙상 검산 없이는 record_review(ok=true) 불가
→ counselor: 리뷰 안 된 제안이 있어서 respond_to_user 거부 → reviewer 로 되돌림 (2~3번)
→ 질문 한도도 이미 써서 월 저축액을 물을 수 없음
→ strategist: "검증 불가" 라며 제안을 지움 → 쟁점만 알리고 끝
```

- 12/13에는 reviewer가 지금 월 저축을 0으로 보고 필요 월 저축 240,000원을 그대로 부족분으로 넣어 통과했다. **같은 상황인데 판단이 그때그때 달랐다.**
- 강제 마무리가 아니라 **에이전트가 규칙을 지키다 스스로 제안을 지운** 경우다. 고칠 곳은 하네스 규칙이다.
- 두 피드백에서 바통 16번, LLM 50회, 입력 약 21만 토큰을 쓰고 결과는 제안 0개였다.

### 2.2 월 저축액을 모른다

- `goal_progress` 는 "가입 뒤 끝난 달" 기준이라 12월에는 `months_done: []` 이다.
- P1 가입 전 3개월에는 급여(월 2,330,000원)가 그대로 있다. 하지만 `spending_summary` 의 지출만 빼면 월 70~90만 원이 남는 것처럼 나온다 (9월 904,500 / 10월 696,400 / 11월 731,800). 지금 모은 돈 80만 원과 맞지 않는다.
- 이유: 지출 집계에 **이름 없는 이체, 저축 이체**가 빠진다. P1에는 여행 적금 월 20만 원이 있다 (페르소나 정의). 매달 33,000원 입금 3번은 정산 입금으로 보이며 수입이 아니다.
- **지금 도구로 바로 계산하면 크게 틀린다.**

### 2.3 이미 수락한 제안을 다시 낸다 (개선 전 실행)

| 제안 | 처음 수락 | 다시 낸 날 | 그사이 실제 거래 |
|---|---|---|---|
| 소리랑 뮤직 해지 | 12/20 | 12/31 수락, 1/10 보류 | 마지막 결제 12/7, 1/7 결제 없음 (해지됨) |
| 무비온 해지 | 12/20 | 12/31 수락, 1/10 보류 | 마지막 결제 12/3, 1/3 결제 없음 (해지됨) |
| 웹툰패스 해지 | 1/10 | 1/24, 1/31 수락 | 1/5 결제는 수락 전, 수락 뒤 결제 없음 |
| 배달 주 1회 줄이기 | 12/20 | 1/24, 1/31 수락 | 계속 줄이는 중 |

- ⚠️ 채점: 하네스 수락 목록에 같은 제안이 여러 번 들어갔다. 반응 규칙이 효과를 겹쳐 적용했다면 개선 전 절약 효과(약 11.8만 원)가 부풀었을 수 있다. C 확인 필요.

## 3. 개선 항목

각 항목에 **무엇을, 왜, 어떻게, 어떻게 확인하나, 담당·의존**을 적는다.

### A. 정확도

#### A1. 가입 주는 목표안까지, 절약 제안은 다음 주부터 (우선순위 1) — PR #22 반영해 고침

- **배경:** PR #22(C)에서 온보딩을 바꿨다. 목표는 대화로 정하고, strategist 가 보고서(달마다 남는 돈)·목표안을 만들고, reviewer 가 `check_goal` 로 검산한다. 그래서 "가입 때 strategist·reviewer 를 부르지 않는다"는 처음 안은 맞지 않다.
- **무엇:** 가입 피드백에서는 보고서·목표안까지만 낸다. **절약 제안(`propose_action`)은 첫 주간 피드백부터** 한다.
- **왜:** 2.1. 가입 때 제안까지 만들면 검산이 막혀 지우는 일이 생겼다. 가입 때는 목표 합의가 먼저다.
- **어떻게:** 온보딩일 때 strategist 의 `propose_action` 을 막거나, 목표안 검산(`check_goal`)에서 제안 절감을 빼고 남는 돈만으로 본다. 줄여야 할 금액은 보고서에 숫자로만 보여 준다.
- **확인:** P1 12/1 의 LLM 호출·입력 토큰, 목표안 채점(`goal`), 12/6 에 제안이 나오는지.
- **결정 필요:** 지금 PR #22 흐름은 온보딩에서도 `propose_action` 을 쓴다 (목표안이 닿는지 보려고). 가입 때 제안을 낼지는 C와 맞춘다.

#### A2. 월 남는 돈: LLM 계산과 코드 계산 비교 (우선순위 1) — PR #22 반영해 고침

- **배경:** PR #22 팀 결정은 "남는 돈 = 수입 − 지출, **내역에서 걸러 계산하는 것은 에이전트 몫**"이다. strategist 가 `flow_summary` 로 달 합계를 보고, 어떤 거래를 빼고 넣을지 정한 뒤 `calculate_many` 로 계산해 `set_report` 한다. 채점에 `report`(월 남는 돈 오차)와 정답 `facts.cashflow` 가 생겼다.
- **바로 고친 것 (사후 리뷰, PR #26):** 보고서의 남는 돈은 이번에 **직접 계산한 값만** 받는다 (도구 결과의 원시 합계를 그대로 못 쓴다). 달별 `수입 − 지출 = 남는 돈`, 평균 = 달별 평균을 코드가 확인한다. 모아 둔 돈은 고정 답변 값을 쓴다.
- **다음 (제안):** 무엇을 빼고 넣을지(카드대금·충전·정산·환불·저축 이체·생활 이체)는 규칙으로 정해진 일이라 코드로도 계산할 수 있다. 같은 P1~P5 에서 **LLM 계산 vs 코드 계산의 `report` 오차**를 비교해, 코드가 더 정확하고 싸면 코드 값을 기본으로 주고 LLM 은 설명·확인 질문만 하게 바꾼다.
  ```
  남는 돈 = 정기 수입 − 실제로 나간 돈
     수입: 급여 · 용돈 · 알바비 (정산 입금 · 환불은 수입이 아니라 지출에서 뺀다)
     나간 돈: 지출 + 생활 이체(월세 등) + 현금 인출 (카드대금 · 충전은 이중 집계라 뺀다)
     저축 이체는 남는 돈에 넣는다 (PR #22 정의)
  ```
- **담당·의존:** C 와 비교 실행 방법을 맞춘다. 코드 계산은 `baseline/tools.py`(C) 또는 Swarm 전처리(A) 중 어디에 둘지 정한다.

#### A3. 부족분 미확인 처리 (우선순위 2)

- **무엇:** 월 저축액을 모르거나 추정 신뢰가 낮으면, **필요 월 저축액을 기준**으로 검산하고 `"기준: 필요 월 저축액 (현재 저축 미확인)"` 이라고 표시한다.
- **왜:** 2.1. 12/13에 reviewer가 한 판단을 코드 규칙으로 고정한다.
- **어떻게:**
  - `check_gap_coverage` 에 `basis` 칸 추가 (`shortfall` / `required_only`).
  - `record_review` 는 부족분 충족과 **제안 안전성**(보호 지출 침해, 근거 없음)을 따로 본다. 부족분을 몰라도 안전하면 통과한다.
  - counselor 메시지에 "부족분은 저축액이 확인되면 다시 볼게요"를 넣는다.
  - strategist가 "검증 불가"를 이유로 제안을 지우려 하면 이 경로를 안내한다.
- **확인:** 단위 테스트(월 저축 없음 → 통과 가능), P1 12/6 제안 수.

#### A4. 질문 우선순위 (우선순위 3)

- 월 저축액을 크게 바꾸는 불분명한 이체(월세인지, 내 다른 계좌인지, 가족 송금인지)가 있으면 analyst의 첫 질문으로 올린다. 지난 실행은 질문 한도를 다른 질문에 먼저 썼다.

### B. 기억과 추적

#### B1. 수락 후 성과 추적 (우선순위 2)

- **무엇:** 수락한 제안의 결과를 **코드가** 판정한다.
  | 행동 | 판정 |
  |---|---|
  | 해지 | 수락일 뒤 다음 결제 예정일(반복 주기로 계산)이 지나도 그 가맹점 결제가 없으면 `해결` |
  | 줄이기 | 수락 전 4주 기준 대비 주당 횟수·금액 변화를 기록 (`진행 중` / `유지` / `되돌아감`) |
  | 저축 늘리기 | 저축 이체 금액·횟수 변화 |
- **왜:** 2.3, 2.4. 해결 판정이 없어서 같은 제안을 다시 냈고 쟁점도 끝나지 않았다.
- **어떻게:** 전처리에 `outcomes` 를 추가해 작업판에 넣는다. 해결된 쟁점은 메모리에서 빠진다.
- **확인:** P1에서 1/10 이후 소리랑·무비온이 해결로 바뀌는지, "해결 갱신" 지표.
- **참고:** 생존 분석 같은 통계 모델은 쓰지 않는다. 사용자 1명·2개월 데이터로는 사건 수가 너무 적다. 규칙 판정으로 충분하다.

#### B2. 피드백 사이 쿨다운 (우선순위 2)

| 이전 반응 | 규칙 |
|---|---|
| 수락 (같은 대상 + 같은 행동) | 다시 못 낸다. 수락 뒤 그 가맹점 결제가 또 나오면 "해지가 안 됐어요" 확인으로만 다시 꺼낸다 |
| 거절 | 4주 동안 못 낸다 |
| 보류 | 2주 뒤 한 번만 다시 묻는다 |

- `propose_action` 에서 코드가 막는다 (프롬프트에만 맡기지 않는다). 기간 값은 실험용 초기값이다.

#### B3. 프로필 항목에 출처 · 상태 · 만료 (우선순위 2)

- **무엇:** 메모리의 사용자 정보를 네 종류로 나눈다.
  | 종류 | 예 | 규칙 |
  |---|---|---|
  | 직접 입력 | "취미 지출은 유지하고 싶어요" | 최우선. 사용자만 바꾼다 |
  | 거래 관찰 | 매주 금요일 배달 | 기간·근거 거래 ID를 남긴다 |
  | 추정 (확인 전) | "커피는 습관적 소비일 수 있음" | 확인 전까지 결정에 쓰지 않는다. 질문 후보로만 |
  | 일시적 상황 | "이번 달은 시험 기간" | 만료일이 지나면 지운다 |
- **왜:** "시험 기간이라 배달이 많았다"가 영구 성향이 되거나, 거래 시간만 보고 "스트레스 소비"로 단정하면 이후 제안이 계속 틀어진다. **거래 시간·반복은 관찰된 사실이지만 이유는 가설**이다.
- **어떻게:** `UserMemory.profile` 항목을 `{value, kind, source, evidence, observed_at, expires_at}` 로 바꾼다 (지금은 `{value, kind, evidence}`). 만료 처리는 코드가 피드백마다 한다.
- **확신도 숫자는 쓰지 않는다.** LLM이 0.76 같은 값을 만들면 안 된다. 코드가 계산하는 방법을 정하기 전까지는 `확인됨` / `추정` 만 쓴다.

### C. 입력 준비 (LLM 전에 코드가)

#### C1. 코드 쟁점 탐지 `data/signals.py` (우선순위 3)

- **무엇:** LLM에 넣기 전에 신호를 코드로 계산하고, 영향 × 확실도 순으로 **상위 5~7개**만 넘긴다.
  | 신호 | 방법 |
  |---|---|
  | 반복결제 · 새 구독 · 가격 인상 · 무료체험 전환 | 지금 `recurring_payments` |
  | 중복 구독 | 같은 소분류(OTT, 음악) 2개 이상 |
  | 습관 지출 급증 | 소분류별 주간 금액의 중앙값 + MAD, 2주 연속일 때만 |
  | 주말 · 야간 몰림 | 요일·시간 비중 |
  | 정산 후보 | 대표 결제 뒤 N일 안에 들어온 입금 |
  | 수입 감소 | 정기 수입 변화 |
  | 분류 의심 | 가맹점과 분류 불일치 |
  | 목표 진척 | 지금 `goal_progress` |
- **왜:** 2.4. 쟁점 난립과 비용. 같은 계산을 매번 LLM이 다시 하지 않게 한다.
- **확인:** 쟁점 재현율 유지 + 정답과 안 맞는 쟁점 감소 + 입력 토큰.
- **담당:** B(데이터)와 나눠서 한다.

#### C2. 원본 거래는 필요한 만큼만 (우선순위 3)

LLM이 원본을 봐야 숨은 맥락을 잡는다. 그렇다고 매번 전부 볼 필요는 없다.

| 시점 | 누가 | 무엇을 |
|---|---|---|
| 가입 | analyst | 가입 전 전체 거래를 압축 형태(날짜·가맹점·금액·분류)로 한 번 |
| 주간 | analyst | 새 거래 + 신호로 설명되지 않은 거래 + **바뀐 쟁점 범위**의 원본 |
| 주간 | strategist | 쟁점별 관련 거래만 |
| 주간 | reviewer | 근거 거래만 |
| 주간 | counselor | 원본 없음 (작업판만) |
| 월말 | analyst | 한 달 요약을 한 번 훑기 |
| 큰 변화 (수입 변화, 새 목표) | analyst | 넓게 다시 읽기 |

#### C3. 규칙 게이트 (우선순위 4)

- 새 거래가 거의 없고, 신호·목표 진척·쟁점 상태가 바뀌지 않은 주는 **LLM을 부르지 않고** 정해진 짧은 메시지(또는 무응답)로 끝낸다.
- 실시간 모니터링처럼 표현하지 않는다 ("새로 확인할 건 없었어요").

### D. 사용자 이해 (개인화)

팀원 제안("Adaptive User Understanding & Care System")을 지금 구조에 맞춰 고른 것이다. **새 에이전트를 늘리지 않고**, 대부분 코드 계층과 기존 에이전트 역할로 대응한다.

| 제안의 컴포넌트 | 지금 구조에서 |
|---|---|
| User Understanding Engine | 코드: 메모리 갱신 + 신호 계산(C1) + 만료 처리(B3) |
| Profile Update Agent | analyst 의 `understand` (지금 있음) + 확인 질문 |
| Intervention Policy · Notification Guard | 규칙 게이트(C3) + 쿨다운(B2), 코드 |
| Care & Report Agent | counselor (말투 선호 반영) |
| Outcome Agent | 성과 추적(B1), 코드 |

#### D1. 온보딩 질문 4~5개를 에이전트 행동과 연결 (우선순위 2)

질문은 프로필 수집용이 아니다. **답 하나하나가 에이전트 행동을 바꿔야 한다.**

| 질문 | 들어가는 곳 | 바뀌는 행동 |
|---|---|---|
| 돈을 모으는 가장 큰 이유 | 목표 | 메시지를 목표 기준으로 |
| 절대 줄이고 싶지 않은 소비 | 보호 지출 (직접 입력) | strategist 후보에서 제외, 실제 거래에서 구체 항목 확인 |
| 관리가 어려운 이유 (귀찮음 · 충동 · 잊음 · 정보 부족) | 전략 우선순위 | 귀찮음 → 구독 정리 등 한 번에 끝나는 것 먼저, 잊음 → 결제일 전 알림 |
| 원하는 말투 (다정 · 숫자 · 간결) | counselor 입력 | 응답 길이와 톤 |
| 점검하기 편한 요일·시간 | 피드백 일정 | 주간 피드백 요일 |

- 모든 질문은 건너뛸 수 있고 나중에 바꿀 수 있다.
- 답은 **초기 가설**이다. 사용 중 행동이 다르면 확인 질문으로 고친다.

#### D2. "AI가 이해한 나" 화면 (우선순위 3, 프로토타입)

- 에이전트가 알고 있는 정보를 출처(직접 입력 / 거래 패턴 추정 · 확인 필요)와 함께 보여 주고, 사용자가 **직접 고칠 수 있게** 한다.
- 잘못 이해한 정보가 이후 제안에 계속 반영되는 문제를 막는다. 발표에서 차별점으로 보여 주기 좋다.
- 데이터는 B3 구조를 그대로 쓴다.

#### D3. 전략 유형 단위로 기억 (우선순위 3)

- 개별 제안("커피 줄이기 거절")을 넘어 **유형**("끊기형 싫어함, 비교·대체형 좋아함")을 기록한다.
- 한 번의 거절로 일반화하지 않는다. 같은 유형 거절이 2번 이상이거나 사용자가 직접 말했을 때만 기록한다.

#### D4. 표현 규칙 (우선순위 2, 프롬프트)

- 죄책감을 주는 표현 금지: "이번 주에도 과소비했어요" 대신 "이번 주에는 평소와 다른 지출이 있었어요. 함께 볼까요?"
- **응원도 검증된 사실로만:** 확인되지 않은 절약을 "5만 원이나 아꼈어요!"처럼 말하지 않는다. 숫자 검증 규칙과 같다.

#### D 에서 빼거나 미루는 것

| 항목 | 이유 |
|---|---|
| MBTI로 소비 성향 예측 | 하지 않는다. 넣더라도 선택 항목인 자기소개 수준이고 우선순위가 낮다 |
| 알림 시점 학습 (JITAI), Contextual Bandit | 열람·미루기 같은 앱 사용 데이터가 필요하다. 데모 시뮬레이터에는 없어서 지금은 평가할 수 없다 |
| 확신도 숫자 | 계산 방법을 정하기 전에는 쓰지 않는다 (B3) |
| 제안서에 인용된 연구 | 아직 확인하지 않았다. 발표 자료에 넣기 전에 출처를 확인한다 |

### E. 검색 (완료 · 검토 중)

- 제공자는 GPT 웹 검색으로 정했다. 화면에 띄우기 전 규칙 필터(링크 정리, 출처 등급, 기준일, 중복 제거, 관련도, 접은 결과는 "N건 더 보기")를 둔다. → PR #20 (`docs/06`), B·C 확인 필요.
- 검색 결과는 여전히 에이전트 입력·저장·계산에 쓰지 않는다.
