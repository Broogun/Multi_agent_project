# 08. 데모 데이터 안내

데모 사용자 5명(P1~P5)의 거래 데이터가 무엇이고, 어디에 있고, 누가 무엇을 써도 되는지 정리한다. 형식의 기준은 [02-specs](02-specs.md)("통합 거래내역 형식", "사용자 기록", "데모 데이터 공유")이고, 결정 배경은 리포트([생성기](reports/261126-1356-c-demo-transactions.md), [Supabase 공유](reports/261126-1611-c-demo-supabase.md))에 있다.

## 1. 한눈에
- **가상 데이터**다. 가맹점·기관·앱 이름과 금액은 모두 데모 값이고 실제 가격·요금이 아니다.
- **입력 경로 B 가정**: 유저가 자산관리 앱에서 내보낸 **통합 거래내역 CSV**를 올린다. 카드·계좌·간편결제는 앱이 이미 합쳤으므로, 우리는 기관 간 통합 코드를 만들지 않는다 (팀 확인 대기).
- **생성기가 만든다** (`src/spending_agent/demo/`). 같은 페르소나는 항상 같은 결과가 나온다. 숫자는 모두 생성 코드가 계산했다.
- **시간 설정**: D0 = 2026-12-01 (온보딩 날)
  - 온보딩: 2026-09-01 ~ 11-30 (3개월) 거래가 한 번에 들어온다
  - 운영: 12-01 ~ 12-14 (14일) 거래가 하루씩 들어온다

## 2. 서비스 흐름과 데이터
| 단계 | 들어오는 데이터 | 에이전트가 할 일 |
|---|---|---|
| 온보딩 | 고정 질의 답변 → 3개월치 거래 CSV | 패턴 파악 → 추가 질의 (반복) |
| 운영 | 매일 그날 들어온 거래 (분석은 시작하지 않음) | 기다린다 |
| 운영 | 유저 기록 (거래에 대한 메모) | 기존 패턴 + 목표 + 새 기록으로 피드백 |

- 밤 10시 이후 거래는 다음 날 들어온다. 그래서 거래가 들어오기 전에 기록이 먼저 올 수 있고, 이때 기록의 `transaction_id`는 `null`이다.
- 현금 기록처럼 연결할 거래가 아예 없는 기록도 있다.

## 4. 통합 내역에 남아 있는 현실 문제
앱이 합쳐 준 내역이라도 아래 문제는 그대로 있다. 적재·분석 코드와 에이전트가 처리해야 하고, 평가 케이스가 여기서 나온다.
- **이름 없는 이체**: 월세·적금·생활비·축의금은 `이체/미분류 출금`으로, 용돈·알바비·정산은 `수입/미분류 입금`으로 보인다. 급여만 `급여`로 보인다.
- **앱 자동 분류 오류**: 상호 기준이라 틀릴 수 있다 (예: 학생식당이 생협 상호라 `쇼핑`).
- **신용카드 대금**: 결제 행과 별도로 매달 `이체/카드대금` 행이 나온다. 같은 돈이라 둘 다 세면 이중 집계다.
- **할부**: 결제일에 전액 1행으로 나오고 `결제수단`에 `할부 N개월`이 붙는다.
- **환불**: 원래 결제와 따로 `가맹점(취소)` 양수 행으로 나온다.
- **현금**: `ATM 출금`만 보이고 실제로 쓴 곳은 보이지 않는다.
- **간편결제 머니**: 충전은 `이체/충전`이고, 결제는 별도 지출 행이다.
- **대표 결제 후 1/n 정산**: 결제 1행 + 이름 없는 `입금` 여러 행으로 보인다.
- **늦은 동기화**: 밤늦은 거래는 다음 날 들어온다.

## 5. 어디에 있나
| 위치 | 내용 | 받는 법 |
|---|---|---|
| 내 PC `data/demo/<ID>/` | `onboarding/transactions.csv`, `daily/YYYY-MM-DD/transactions.csv`, `records.json`, `truth.json`, `manifest.json` | `uv run python -m spending_agent.demo build P4` (git 제외, 언제든 재생성) |
| Supabase 스키마 `demo` | `personas`, `transactions`, `records` | 프로젝트 초대 → Table Editor ([07 §5](07-onboarding.md)) |
| Supabase 스키마 `demo_eval` | `truth`, `cases`, `tx_truth`, 뷰 `tx_compare` | 위와 같음. 평가할 때만 본다 |
| 저장소 `src/spending_agent/demo/personas/P*.toml` | 생성 규칙, 고정 질의 답변, 숨은 사실, 얽힌 문제, 운영 시나리오, 평가 케이스 | 원본. 데이터를 바꾸려면 여기를 고친다 |

## 6. 누가 무엇을 써도 되나
| 데이터 | 앱(C) | 에이전트(A) | 평가(B) |
|---|---|---|---|
| 통합 거래내역 (`transactions.csv`, `demo.transactions`) | 화면에 표시 | 적재·집계 결과를 통해 사용 | 사용 |
| 유저 기록 (`records.json`, `demo.records`) | 입력 화면 시연 | 분석 시작 계기 | 사용 |
| 고정 질의 답변·숨은 사실 (`truth.json`의 `user_sim`) | 쓰지 않음 | **입력 금지** (유저 시뮬레이터만 사용) | 시뮬레이터로 사용 |
| 정답 (`truth.json`의 `facts`·`rubric`, `demo_eval`) | 쓰지 않음 | **입력 금지** | 채점 기준 |

- `truth.json`(정답)은 가상 세계 기준의 정답이다.
  - `facts`: 생성 코드가 계산한 사실 (실제 용도, 월별 순지출, 목표 부족액, 지렛대 크기, 정산·환불·카드대금·할부 묶음)
  - `user_sim`: 고정 답변과 숨은 사실
  - `rubric`: 얽힌 문제와 평가 케이스의 `expect`/`must_not`. 정답 문장이 아니라 판단 기준이다
- 에이전트가 말하는 숫자는 계산 함수 결과여야 한다 (05 §3). `facts`의 숫자는 채점할 때 비교용으로만 쓴다.

## 7. 명령
```
uv run python -m spending_agent.demo build P4                         # 온보딩분 (기존 출력은 지우고 다시 만듦)
uv run python -m spending_agent.demo build P4 --through 2026-12-14    # 운영 날짜까지
uv run python -m spending_agent.demo advance P4 --days 1              # 하루 넘기기 (그날 거래 + 기록)
uv run python -m spending_agent.demo publish                          # Supabase에 올림 (올리는 사람만, --group supabase)
uv run --group supabase pytest -m live                                # 공유 DB가 생성기 결과와 같은지 (읽기만)
```

## 8. 데이터를 바꾸려면
1. `personas/P*.toml`을 고친다. 파일 맨 위 주석에 그 페르소나의 얽힌 문제와 함정이 적혀 있다.
2. `uv run pytest`를 돌린다. 페르소나별 스토리 테스트(`tests/test_demo_data.py`)가 깨지면 스토리가 바뀐 것이니 케이스와 같이 고친다.
3. PR이 머지되면 올리는 사람이 `publish`해서 공유 DB를 맞춘다. live 테스트가 공유 DB와 생성기의 차이를 알려 준다.

## 9. 알려진 한계
현재 버전(P1~P5)으로 진행한다. 3개월 내역만으로 쟁점 신호는 잡히지만 현실보다 반복적이고 깨끗하다. 가맹점 다양성과 일회성 지출 부족, 공휴일·관리비 미반영, 정답 월별 집계 기준 같은 점검 결과와 다음 버전 후보는 [데모 데이터 점검 리포트](reports/261126-1708-c-demo-data-audit.md)에 있다.

## 10. 가정·미확인
- 실제 자산관리 앱 내보내기 파일의 열 구성 (실제 파일의 헤더 줄로 맞출 예정)
- 이체 적요에 상대 이름이 빠지는지 ([2021년 보도](https://www.etnews.com/20210122000137) 기준 가정)
- 앱이 카드대금·할부·ATM 출금·이름 없는 이체를 어떻게 분류하는지
- 고정 질의 목록과 유저 기록 형식은 아직 임시다 (`contracts.py` 합의 전)
