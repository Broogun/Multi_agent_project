## 검색 창 이벤트 (search → app)

검색 모듈이 UI로 보내는 유일한 형식. 에이전트에게는 `panel_id`와 "표시함" 사실만 돌아간다.

```json
{
  "type": "search_panel",
  "panel_id": "8자리",
  "query": "상품명 + 용량 (개인정보 없음)",
  "text": "검색 답변 (수정 금지)",
  "suggestions_html": "제공자가 보내는 검색 제안 HTML 또는 null (있으면 그대로 렌더링)",
  "sources": [{"title": "...", "uri": "..."}],
  "notice": "검색 결과이며, 실제 가격은 판매처에서 확인하세요."
}
```

외부 검색 제공자는 미정이며 실제 연동은 보류한다. 기존 이벤트의 필드와 타입은 유지하고, 화면은 `fakes.fake_search_panel` 로 먼저 개발한다.

## 사용자 확인 가격 (app → data)

| 필드 | 필수 | 설명 |
|---|---|---|
| user_id | ✅ | |
| product_name | ✅ | |
| size, unit_size, unit | | 용량 (단위가격 계산용) |
| price | ✅ | 원, 정수 |
| seller | | 판매처명 |
| checked_date | ✅ | 사용자가 확인한 날 |
| source_type | ✅ | `user_verified` / `receipt_ocr` / `capture_ocr` |

저장하지 않는 것: 상품 설명, 이미지, 페이지 텍스트, 검색 결과. 캡처 원본은 확인 후 삭제.

## 계산 결과 형식 (data → agent)

```json
{"status": "ok | needs_check | no_data | stale", "value": {}, "calc": {"항목": "계산식 문자열"},
 "sources": [{"id": "", "name": "", "as_of": ""}], "as_of": "", "caveats": []}
```
`status`가 `needs_check`/`no_data`면 에이전트는 숫자를 말하지 않는다.

## 통합 거래내역 형식 (입력 경로 B 가정, 초안)

유저가 자산관리 앱(마이데이터)에서 내보낸 통합 거래내역 CSV를 올린다고 가정한다. 카드·계좌·간편결제 통합은 앱이 이미 했으므로 **우리는 기관 간 통합 코드를 만들지 않는다.** 데모 생성기 [`spending_agent.demo`](../src/spending_agent/demo/__init__.py)가 이 형식으로 만든다. 열 구성은 임시이며 실제 앱의 내보내기 형식과 같은지는 **미확인**이다 (실제 파일의 헤더 줄로 확인 예정).

- 위치: `data/demo/<페르소나>/` (git 제외). `onboarding/transactions.csv`는 D0 이전 3개월치, `daily/YYYY-MM-DD/transactions.csv`는 그날 새로 들어온 거래
- 인코딩 UTF-8 (BOM 포함, 엑셀에서 바로 열림). 기간·건수는 `manifest.json`
- `truth.json`은 평가 전용 정답 데이터. 적재·분석 코드와 에이전트 입력에 넣지 않는다. 구성: `facts`(생성 코드가 계산한 사실: 실제 용도, 월별 순지출, 목표 부족액, 지렛대 크기, 더치페이·환불 묶음), `user_sim`(고정 질의 답변·숨은 사실, 유저 역할 시뮬레이터용), `rubric`(얽힌 문제·평가 케이스, 우리가 정한 채점 기준). 모두 가상 세계 기준이다

| 열 | 설명 |
|---|---|
| 거래ID | 행 식별. 실제 내보내기에는 없을 수 있다 (그때는 적재할 때 부여) |
| 날짜, 시간 | `YYYY-MM-DD`, `HH:MM` |
| 타입 | `지출` / `수입` / `이체` (앱이 붙인 값) |
| 대분류, 소분류 | 앱 자동 분류. 틀릴 수 있다 |
| 내용 | 가맹점명(카드 결제는 상호 그대로), 이체는 `입금`/`출금`, 환불은 `가맹점명(취소)` |
| 금액 | 원, 정수. 지출·출금은 음수, 수입·환불은 양수 |
| 결제수단 | 연결된 계좌·카드·간편결제 이름 |
| 메모 | 앱 메모 (데모에서는 비어 있음) |

통합 내역에 남는 현실 상황 (적재·분석 쪽에서 처리할 것):
- 이체 상대 이름이 없다 ([2021년 보도](https://www.etnews.com/20210122000137) 기준 가정, 현재 미확인). 그래서 앱이 월세·적금은 `이체`로, 용돈·알바비·정산 입금은 `수입/미분류`로 분류한다
- 앱 자동 분류는 상호 기준이라 틀릴 수 있다 (예: 학생식당이 생협 상호라 `쇼핑`)
- 현금은 `ATM 출금`(지출/현금)만 보이고 실제 쓴 곳은 보이지 않는다
- 간편결제 머니 충전은 `이체/충전`으로, 머니 결제는 별도 지출 행으로 나온다
- 환불은 원래 결제와 따로 양수 행으로 나온다 (반품이 잦으면 결제 총액과 순지출 차이가 크다)
- 신용카드는 결제 행과 별도로 매달 결제일에 `이체/카드대금` 행(`○○카드 결제대금`)이 나온다. 같은 돈이라 둘 다 지출로 세면 이중 집계다. 첫 달 대금은 내역 이전 사용분이다
- 할부는 결제일에 전액 1행으로 나오고 `결제수단`에 `할부 N개월`이 붙는다. 현금흐름은 카드대금에 회차로 나뉜다
- 대표로 결제하고 나머지 사람에게 1/n 을 받는 경우(회식, 가족결합 통신비)는 결제 1행 + 이름 없는 `입금` 여러 행으로 보인다
- 회사 급여이체는 적요에 `급여`가 찍혀 `수입/급여`로 보인다 (개인 이체만 이름이 없다고 가정)
- 밤늦은 거래는 다음 날 들어온다 (`daily/`의 날짜보다 이른 날짜의 행이 있을 수 있음)
- 가맹점·기관·앱 이름과 금액은 모두 가상의 데모 값

## 데모 데이터 공유 (Supabase, 열람용)

팀원끼리 같은 데모 데이터를 보기 위한 공유 DB다. **앱 저장 형식이 아니다** (사용자 데이터 저장 형식은 B가 정하고, 계획은 SQLite 그대로). `uv run python -m spending_agent.demo publish`가 [`schema.sql`](../src/spending_agent/demo/schema.sql)을 실행한 뒤 페르소나별로 지우고 다시 넣는다. 보는 법은 [07 §5](07-onboarding.md).

| 스키마 | 테이블 | 내용 |
|---|---|---|
| `demo` | `personas` | 프로필 요약, D0, 온보딩·운영 기간 |
| `demo` | `transactions` | 통합 거래내역 (CSV 열 + `batch`, `visible_on`) |
| `demo` | `records` | 유저 기록 |
| `demo_eval` | `truth` | `truth.json` 전체 (jsonb) |
| `demo_eval` | `cases` | 평가 케이스 |
| `demo_eval` | `tx_truth`, 뷰 `tx_compare` | 거래별 실제 용도 (앱 분류와 나란히 보기) |

- 정답은 `demo_eval`에만 둔다. `demo`에는 실제 용도·숨은 사실 같은 정답 열이 없다 (테스트로 확인)
- 두 스키마 모두 공개 키(`anon`·`authenticated`)로는 열지 않는다. 대시보드와 DB 연결 문자열(`.env`의 `SUPABASE_DB_URL`)로만 본다
- `--reset`은 두 스키마를 통째로 지운다. 테이블 구조를 바꿨을 때 전체를 다시 올리는 용도다
