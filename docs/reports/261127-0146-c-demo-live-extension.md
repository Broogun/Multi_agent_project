# 데모 데이터를 1/31까지 늘리고 기간 중 쟁점을 더한다 (원래 데이터는 그대로)

## 결론
- LLM 평가(단계 1)를 위해 운영 기간을 **12/1 ~ 1/31**로 늘렸다.
- **원래 데이터는 바꾸지 않고 추가만 했다.** 온보딩 3개월과 12/1~12/14의 거래·기록은 처음 만든 그대로이고, 테스트가 해시로 고정한다. 시연 시나리오(09)와 지금 공유 DB의 2주치는 그대로 쓸 수 있다.
- 페르소나마다 **기간 중 쟁점 3개**, 핵심 기록, **기록 습관 규칙**, 피드백 시점별 정답(쟁점 상태·확인할 케이스·목표 달성도)을 넣었다.

## 배경
- 평가는 온보딩 1번 + 주간(일요일 저녁) 8번 + 월간(말일 저녁) 2번, 페르소나당 피드백 11번으로 돈다 (10 §2). 그런데 데이터는 12/14까지였다.
- 늘리기만 하면 P4는 12/25 월세, P5는 1/19 간편결제 충전에서 잔액이 음수가 되어 생성이 멈췄다. 씨네박스 인상 가격, 휴대폰 약정 뒤 요금, P2 방학 패턴처럼 기간이 끝나면서 어긋나는 곳도 있었다.
- 확정 쟁점이 온보딩 때 것뿐이라, "운영 중에 새로 생긴 쟁점을 잡는지"와 "상태 변화(해결·개선)를 맞게 갱신하는지"를 잴 수 없었다.
- 팀 결정: 원래 데모 데이터를 유지하고 추가하는 방향으로 한다.

## 한 일 / 결정
- **원래 데이터 고정**: `tests/test_demo_live_period.py`에 5명의 원래 데이터(온보딩 + 12/14까지 배치·기록) 해시를 넣었다. 덧붙이는 규칙은 12/15 이후에만 영향을 주는 것만 썼다: `from`이 12/15 이후인 빈도 배율, 월별 금액(`amount_by_month`), 시나리오 이벤트, `skip_months`.
- **피드백 일정** (`generator.feedback_points`): 온보딩 → 일요일 저녁 주간 → 말일 저녁 월간. 1/31은 일요일이라 월간 하나로 합친다. 저녁 9시 뒤에 쓴 기록은 다음 피드백에서 다룬다 (가정). `manifest.json`의 `feedback`에 넣었다. 에이전트가 알아도 되는 일정이다.
- **기간 중 쟁점** (`[[issues]]`): 유형은 일반 목록(`ISSUE_TYPES`, 초안)에서 고른다. `from`(신호가 생기는 날), `detect_by`(이 피드백까지 짚어야 함), `until`(끝나는 날)과 근거 거래를 적는다.
  - 근거 거래가 `detect_by` 전에 들어오지 않으면 생성이 실패한다.
  - 일부러 **서비스와 상관없는 변화**를 넣었다. 좋아졌다고 서비스 덕으로 말하면 틀린다: P1 1월 외식 감소, P2 방학 카페 감소, P3 약정 종료 요금 인하, P4 알바비 회복.
  - 페르소나별 내용은 [08 §3](../08-demo-data.md#3-페르소나-5명)에 있다.
- **잔액 문제**
  - P4: 부모님 추가 송금(12/23, 이름 없는 입금)으로 12월 월세를 버틴다. 1월 적금도 건너뛰게 했다. 넣으면 1/27에 잔액이 음수가 되기 때문이다. 이유는 숨은 사실 H12로 적었다.
  - P5: 12월 부모님 용돈을 건너뛰고 1/26에 다시 드린다. 이것을 "지출 감소처럼 보이는 함정"(미룬 돈) 쟁점으로 삼았다.
- **유저 기록**
  - 쟁점과 이어지는 핵심 기록은 직접 썼다 (5명 합계 11건). 유저 이해가 남겨야 할 내용을 `learn`으로 붙였다. 원래 기록 21건에도 `learn`만 덧붙였다. 출력에는 나가지 않는다.
  - 나머지는 **기록 습관** `[[record_habits]]`로 만든다.
    - 규칙 내용: 실제 용도, 확률, 들어온 뒤 며칠 안에 쓰는지, 문장 틀.
    - 12/15부터 적용한다. 같은 습관은 하루 1건이고, 이미 직접 쓴 기록이 있는 거래는 건너뛴다.
    - 기록 id는 `R-<거래ID>`다.
    - 거래에서 나오므로, 서비스 있음 세계에서 소비가 바뀌면 기록도 따라 바뀐다.
- **시점별 정답** (`truth.facts.timeline`): 피드백 시점마다 ① 쟁점 상태 ② 그때 확인할 케이스 ③ 목표 달성도를 넣었다.
  - 쟁점 상태는 아직·선택·필수·종료 넷이다. 기존 얽힌 문제는 기준 세계에서 내내 "필수"다.
  - 목표 달성도 (`generator.goal_progress`, 가정): 현재 저축액 + **끝난 달**의 (수입 − 지출)을, 필요 월 저축액 × 끝난 달 수와 비교한다.
    - 처음에는 12/1부터의 누적을 써 봤다. 월급(25일) 전에는 −100만 원대로 흔들려서 주간 피드백에 쓸 수 없었다.
    - 그래서 이번 달은 지금까지의 수입·지출만 따로 보여 준다.
    - 목표를 위해 쓴 돈(P2 여행 예약)은 지출이 아니라 목표에 쓴 돈으로 본다.
- **기존 평가 케이스**: 지우지 않고 덧붙였다.
  - 기록 케이스에 `record`를 붙였다. 그 기록 뒤 첫 피드백이 `check_at`이 된다.
  - "기록이 없는 날" 케이스 5개는 금지 문장만 바꿨다: "기록 없이 먼저 피드백을 보낸다" → "피드백 날이 아닌데 먼저 메시지를 보낸다". 주간 피드백은 기록이 없어도 나가므로 원래 문장이 새 구조와 충돌했다.
  - 새 케이스 21개(쟁점별 + 월간 피드백)를 더해 53 → 74개가 됐다.
- **CLI**: `advance`가 하루마다 "기록 → 유저 이해", "저녁: 주간/월간 피드백"을 보여 준다 ("분석 시작" 문구는 뺐다).
