# Gemini SDK 실험: 생성·함수 호출은 동작, 검색 그라운딩은 결제 연결 전이라 막힘

- 날짜: 261125
- 작성: A (Broogun, Claude Code와 작업)
- 관련: `scripts/gemini_sdk_experiment.py`, [06](../06-search-policy.md), 결과 메타데이터 `out/experiments/gemini-261125-*.json` (git 제외)

## 결론
- 기본 생성(E1)과 함수 호출(E3)은 동작한다. 함수 선택은 정확했지만 **인자 형식이 느슨하면 모델이 허용되지 않은 값을 채운다** → 계약에 enum·구조 타입이 필요하다.
- 검색 그라운딩(E2)은 **429 할당량 초과**로 한 번도 성공하지 못했다. 무료 티어에서 Gemini 3 계열 그라운딩은 제공되지 않는 것으로 보인다 (가격 페이지 "Free: Not available"과 일치). 결제 계정 연결 후 다시 실험해야 한다.

## 알게 된 것
1. **LLM은 묻지 않아도 숫자를 만든다.** E1 답변에 "저축 40~50%(100~125만 원)" 같은 근거 없는 수치가 들어갔다. 숫자 검증기(이전 `agent/validator.py`)는 필수다.
2. **`list[dict]` 인자는 모델마다 다르게 채운다.** `calc_bulk_purchase` 의 options 는 필드·단위가 고정된 타입으로, `source_type` 은 Literal(enum)로 선언해야 한다 → B(calc-core) 계약에 반영 제안.
3. **lite 모델이 훨씬 빠르다** (1.7초 대 20.7초). 함수 선택 정확도는 이번 두 사례에서 같았다. 표본이 2개라 결론은 아니다.
4. **모델 ID가 빨리 바뀐다.** 이름을 하드코딩하지 말고 `GEMINI_MODEL` 환경변수로 둔다. 실험 스크립트는 최신 flash 를 자동 선택하도록 고쳤다.

## 버린 대안
- 무료 티어로 그라운딩 우회 (구 모델 사용): 2.5 는 신규 사용자 404, 무료 티어 입력은 학습에 쓰여 원칙과도 맞지 않음.

해석:
- 핵심 원칙(계획 없던 구매 억제, 필요한 구매만 검색, 가격 지어내지 않기)은 lite 모델도 지킨다.
- U4 는 기대치 자체를 다시 정해야 한다: 에어팟 가격을 모르는 상태라 가격을 먼저 묻는 건 합리적이다. 문제는 **스스로 뺄셈한 숫자와 Tool 이름 노출** → 숫자 검증기 + 시스템 프롬프트에 "Tool 이름을 말하지 말 것" 추가.
- U5 → `calc_bulk_purchase` 인자를 구조 타입(필수 unit_size, enum source_type)으로 바꾸자는 제안 근거가 2번 쌓였다.
