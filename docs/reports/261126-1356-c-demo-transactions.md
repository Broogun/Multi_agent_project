# 데모 거래 데이터: 통합 거래내역(입력 경로 B 가정) 생성기와 페르소나 5명

## 결론
입력 경로는 **B(유저가 자산관리 앱에서 내보낸 통합 거래내역을 업로드)**로 가정한다. 데모 데이터는 그 통합 내역 CSV 형태로 만들고, **카드·계좌·간편결제 통합 코드는 만들지 않는다.** 페르소나 5명(P1~P5)의 초안을 만들었다.

## 배경
- 서비스 흐름은 두 단계다.
  - 온보딩: 고정 질의 → 거래 불러오기 → 패턴 파악 → 추가 질의 (반복)
  - 이후: 거래가 매일 쌓임 → 유저 기록이 들어오면 기존 패턴 + 목표 + 새 기록으로 피드백
- 토스, 현대카드, 뱅크샐러드 같은 앱은 마이데이터로 기관별 내역을 불러와 자체적으로 합친다.
  - 토스: 마이데이터 2.0 보도 ([토스피드](https://toss.im/tossfeed/article/mydata2))
  - 현대카드: 앱 '내 자산' ([카드고릴라](https://www.card-gorilla.com/contents/detail/2117))
- 직접 마이데이터로 연동하려면 허가가 필요하다. 반면 통합 앱의 내보내기 파일은 지금도 받을 수 있다. 뱅크샐러드는 "데이터 내보내기 → 파일로 받기"로 엑셀을 받는다고 안내한다 ([뱅크샐러드 블로그](https://www.banksalad.com/articles/%EA%B0%80%EA%B3%84%EB%B6%80-%EC%97%91%EC%85%80-%EC%96%B4%ED%94%8C-%EC%B6%94%EC%B2%9C-%EC%96%91%EC%8B%9D)).

## 한 일 / 결정
- **형식**: 통합 거래내역 CSV (거래ID, 날짜, 시간, 타입, 대분류, 소분류, 내용, 금액, 결제수단, 메모). 초안은 [02-specs](../02-specs.md)에 있다.
- **통합 내역에 남는 문제는 그대로 넣었다.**
  - 이름 없는 이체: 앱이 월세·적금은 `이체`로, 용돈·알바·정산은 `수입/미분류`로 분류
  - 앱 자동 분류 오류: 학생식당이 생협 상호라 `쇼핑`으로 잡힘
  - 현금(ATM 출금), 환불 행, 머니 충전 행
  - 신용카드 대금 출금(결제 행과 같은 돈), 할부(결제일에 전액 + `할부 N개월`)
  - 대표 결제 후 1/n 정산 입금 (회식, 가족결합 통신비)
  - 밤늦은 거래가 다음 날 들어옴
- **페르소나 파일 1개**(TOML)에 다섯 가지를 함께 둔다: 생성 규칙, 고정 질의 답변, 숨은 사실, 운영 시나리오(이벤트·유저 기록), 평가 케이스.
- **위치**: 코드는 `src/spending_agent/demo/`, 출력은 `data/demo/`(git 제외)에 두고 언제든 재생성한다.
- **재현성**: 난수를 (페르소나, 날짜, 규칙)마다 고정한다. 운영 기간을 늘려도 이전 날짜의 거래는 바뀌지 않는다.
- **유저 기록**: 기록 시점에 이미 들어온 거래만 `transaction_id`로 연결한다. 거래보다 먼저 쓴 기록과 현금 기록은 `null`이다.
- **얽힌 문제**: 페르소나에는 문제 하나가 아니라 서로 얽힌 문제 묶음을 넣는다. 페르소나 파일의 `[[problems]]`에 방향(수입/지출/목표), 지렛대, 제약, 이어지는 작업을 적는다. P4에서는 목표 부족액을 지출 지렛대 하나로는 물론이고 다 합쳐도 메울 수 없다. 복합 케이스(C14~C16)는 원인 하나로 단정하지 않는지, 제약 충돌과 순서 있는 작업을 처리하는지 본다.
- **정답(ground truth) 분리**: `truth.json`을 세 부분으로 나눈다. 모두 평가 전용이고 가상 세계 기준이다.
  - `facts`: 생성 코드가 계산한 사실 (실제 용도, 월별 순지출, 목표 부족액, 지렛대 크기, 더치페이·환불 묶음, 기록-거래 연결)
  - `user_sim`: 고정 답변과 숨은 사실 (유저 역할 시뮬레이터용)
  - `rubric`: 얽힌 문제와 케이스. 우리가 정한 채점 기준이고 정답 문장이 아니다
- **이름과 금액**: 가맹점·기관·앱 이름은 가상이고 금액은 데모 값이다.
- **월 여유를 목표 부족분보다 작게 맞춘다**: 여유(수입 − 지출)가 부족분보다 크면 "저축을 늘리면 된다"로 끝나서 복합 문제가 되지 않는다. 처음 넣은 금액에서는 P1·P2·P3·P5의 여유가 월 30만~140만 원이었고, 실수령과 생활비를 조정해 0 근처로 맞췄다.
- **seed 선택**: 확률로 만든 데이터가 스토리를 보여주지 못하는 표본일 수 있어서 seed를 비교해 골랐고, 이유는 페르소나 파일에 적었다.
  - P4: 6 (9~11월 변동지출이 고름)
  - P2: 27 (카페가 9월 8건 → 11월 18건, 중간고사 기간에 몰림)
  - P5: 14 (쇼핑의 75%가 월급 직후, 반품 5건, 월 수지 0 근처)
  - P1·P3: 기본값으로 스토리가 나와 그대로 둠
- **생성기 확장** (P4 출력은 바이트 단위로 같음): 신용카드 대금, 할부, 고정비 정산(1/n), 정기결제 시작일·월별 금액, 기간·날짜별 빈도 배율, 반품.

## 버린 대안
- 기관별 원천 3종(계좌·카드·간편결제)으로 만들고 우리가 합치기: 처음엔 이렇게 만들었으나 버렸다. 경로 A(마이데이터 직접 연동)는 허가가 필요하고, 경로 B에서는 통합을 앱이 이미 한다. 통합 코드는 만들지 않기로 했다.
- 손으로 쓴 CSV, LLM이 만든 거래: 재현이 안 되고 숫자를 LLM이 만들게 된다 (05 §3).
- 한 명당 전략 하나: 우선순위 판단과 함정(하면 안 되는 것)을 평가할 수 없다.
- 메인 스토리 1개 + 함정 나열 (P4 첫 초안): 신호는 여러 개지만 서로 얽히지 않고 케이스가 신호별로 따로 채점돼서, 조합·우선순위 판단을 시험하지 못한다.
- 실제 브랜드 이름·실제 앱 형식 흉내: 확인하지 않은 가격·형식을 사실처럼 쓰게 된다.
- YAML: `pyyaml` 의존성이 추가된다. TOML은 표준 라이브러리 `tomllib`로 읽는다.
