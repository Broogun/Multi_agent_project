# 압축 메모리 Swarm 코어 (Phase 1): 구현 결정과 리뷰 반영

- 날짜: 261127
- 작성: A (Broogun)
- 관련: [Swarm 설계 계획](../architecture/memory-backed-swarm-plan.md), [싱글 기준선 하네스 리포트](261127-1119-c-single-agent-baseline.md), PR #17 · 후속 PR, 코드 `src/spending_agent/agent/swarm.py`

## 결론
- 설계 계획 Phase 1 범위(에이전트 4명, `handoff_to_*`, 리뷰어 반려, 압축 메모리, 하네스 가드)를 `agent/swarm.py`에 구현했다.
- `baseline.harness.Agent` 프로토콜을 구현해 싱글 에이전트와 같은 하네스·도구·채점으로 비교된다 (`--agent swarm`).
- **가짜 LLM으로만 검증했다.** 실제 모델 비교는 기록 응답 정책 합의 뒤에 한다.

## 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| 그래프 | LangGraph `Command(goto=...)` 대신 같은 의미의 홉 루프를 직접 구현 | 기준선 하네스가 호출 단위(피드백·유저 이해)로 부르므로, 한 피드백 안의 홉만 돌면 된다. 그래프 이전은 HITL 재개(Phase 3) 때 |
| 기록 응답 | 하네스 기준(말하지 않음)대로 analyst 가 메모리만 갱신 | 설계 계획의 "기록 시 리캡" 은 팀 합의 전 |
| 질문 권한 | `ask_user` 를 analyst·counselor 둘 다 사용 | 설계대로 counselor 만 물으면 질문 하나에 홉이 2번 늘어난다. 한도는 하네스가 똑같이 강제 |
| 전략가 | 1명 (계산·습관 도구 통합) | 설계 계획 §3.3 |
| 기존 3분할 코드 | `agent/state.py`·`tools.py` 는 그대로 둠 | Swarm 이 비교에서 이기면 정리 |

## 하네스가 코드로 강제하는 것
- 규칙 전처리 4개(반복결제·가격 변화·새 결제, 카드대금, 목표 달성도, 이름 없는 이체) → 작업판에 요약만. 목록은 최근 것부터 자른다.
- 정기 이체 표시: 서로 다른 달 2번 이상, 달마다 1~2번, 날짜 차이 3일 이내. 한 번에 몰린 정산 입금은 정기가 아니다.
- 홉 한도 8, 반려 한도 2 → counselor 강제 마무리. 강제 마무리 중 counselor 는 넘길 수 없다. 끝내 응답하지 못하면 고정 문구로 끝난다 (빈 메시지 없음).
- 제안 절감액·부족분은 **이번에 calculate·forecast_goal 로 직접 계산한 값만**. 조회 결과의 날짜·거래ID·개별 금액, 검산 기록의 남은 부족분은 허용하지 않는다.
- 제안이 바뀌면 검산·리뷰를 다시 받는다. 리뷰 결과는 boolean `true` 또는 문자열 `"true"` 만 통과.
- 최종 숫자 검증 실패 시 1회 재작성. 제안 문장에 걸리면 counselor 가 `edit_suggestion_text` 로 문장만 고친다 (절감액·강도는 못 바꿔 리뷰 유지).
- 제안 강도: 줄이기 `per_week`, 저축 늘리기·상한 `amount`, 바꾸기 `to`(필수), 목표 조정 `deadline`(+`amount`, 절감액 없음).

## 비교할 때 알아 둘 것
- 전처리 결과는 숫자 검증 허용 목록에 들어간다 (설계 §4.2 의도). 그래서 Swarm 의 "첫 답 숫자 통과율" 은 싱글보다 유리하다. 비교 리포트에서 따로 표시한다.
- 비용은 `tool_calls`(에이전트)와 `harness_tool_calls`(전처리)를 따로 본다. 에이전트별 토큰은 `by_agent` 에 있다.
