# 온보딩 목표를 대화로 정하게 바꿈: 보고서·목표안·목표 생성 버튼, 남는 돈 기준, Swarm 온보딩 흐름

- 날짜: 261127
- 작성: C (KIM-YUNHO)
- 관련: [08 데모 데이터 §3](../08-demo-data.md#3-페르소나-5명), [09 시연 3-1~3-5](../09-demo-scenario.md), [10 평가 계획 §2·§3·§5~§7](../10-llm-eval-plan.md), [Swarm 설계 계획](../architecture/memory-backed-swarm-plan.md)

## 결론
- 목표를 고정 질의에서 받지 않는다. 온보딩 흐름은 아래 순서다.
  1. 에이전트가 내역에서 달마다 남는 돈(수입 − 지출)과 패턴을 보여 준다.
  2. 목표를 묻는다.
  3. 보고서와 목표안을 낸다.
  4. 유저가 목표안을 고친 뒤 목표 생성 버튼을 누른다.
  5. 그 뒤 주간·월간 피드백은 만든 목표를 기준으로 한다.
- 데모 거래·기록은 바꾸지 않았다. 원래 데이터 해시 테스트도 그대로 통과한다. 바꾼 것은 유저 쪽 데이터(고정 질의, 원하는 목표, 목표 질문용 숨은 사실, 목표 조정 규칙)와 정답, 평가 케이스다.
- 싱글과 Swarm 둘 다 같은 하네스로 온보딩 목표 흐름을 돈다. 채점에 세 가지를 더했다: 온보딩 보고서 정확도, 목표 대화, 목표 달성(부족분을 메운 비율).
- **가짜 LLM으로만 검증했다.** 실제 모델 비교는 아직이다.

## 팀 결정 (이번 대화)
| 항목 | 결정 |
|---|---|
| 고정 질의 | 남긴다. 목표만 뺀다. 지금 모아 둔 돈(`saved`)은 고정 질의로 받는다 |
| 온보딩 질문 한도 | 5개 (확인 질문 + 목표 대화). 주간·월간은 그대로 3개 |
| 남는 돈 기준 | 수입 − 지출. 수입·지출 값을 내역에서 걸러 계산하는 것은 에이전트 몫이다 |
| 보고서·목표안 형식 | C가 정함 (아래). 화면·계약 후보 |
| 목표 수정 | 유저가 버튼을 누르기 전에 목표안을 고칠 수 있다 |

### 데이터 (`demo/personas/P*.toml`, `generator.py`, `responses.py`)
- **고정 질의**: `goal`을 빼고 `saved`(지금 모아 둔 돈)를 넣었다.
- **원하는 목표** `onboarding.goal_intent` (name·amount·deadline): 유저 시뮬레이터만 본다. 바꿀 수 있는 범위는 목표 조정 반응 규칙(`goal_flex`)의 수락 한도다 (`responses.goal_range`).
  - P1: 수락 규칙 없음 (거절만 새로 둠)
  - P2: 수락 규칙 없음 (거절만 새로 둠)
  - P3: 수락 규칙을 새로 둠
  - P4·P5: 원래 있던 수락 규칙
- **목표 질문용 숨은 사실**
  - `about = "goal"`(무엇·얼마·언제): G1, 5명 모두
  - `about = "goal_flex"`(바꿀 여지): P1~P3은 G2를 새로 넣었고, P4 H8·P5 H7은 기존 사실을 그대로 쓴다
- **정답**
  - `facts.cashflow`: 9~11월 달마다 수입·지출·남는 돈과 평균. 할부를 결제한 달에 전액으로 본 값과 회차로 나눈 값을 둘 다 둔다.
  - `facts.goal`: 원본 페르소나에서는 원하는 목표다. 평가에서는 유저가 만든 목표로 다시 계산한다 (`generator.active_goal`).
- **평가 케이스**: 온보딩 목표 케이스를 남는 돈·목표 대화 기준으로 고쳤다 (P2-C06, P3-C04, P4-C14, P5-C04). P1은 온보딩 케이스 C15를 새로 넣고, C08의 부족분 정의를 "필요 − 남는 돈"으로 바꿨다.

- **P1 원하는 금액을 200만 → 210만 원으로 올렸다.**

  - 210만 원이면 차이가 33,433원이라 이야기가 유지된다. 테스트가 이 관계를 고정한다.

### 유저 시뮬레이터 (`baseline/simulator.py`)
- **목표 질문 답변**
  - 목표 대화 사실은 자기 `targets`만 강한 키워드로 쓴다. 반응 규칙의 '목표' 같은 낱말이 다른 사실과 겹치기 때문이다.
  - 점수가 같으면 질문에 '미루·낮추·바꿀 수' 같은 말이 있는지로 고른다. 있으면 goal_flex, 없으면 goal이다.
  - 5명 × 질문 6가지를 테스트로 고정했다.
- **목표 생성 버튼** `create_goal`
  - 범위 밖인 칸만 고친다. 금액은 [최소, 원하는 금액], 마감은 최대 마감까지, 모아 둔 돈은 실제 값이다.
  - 목표안이 없거나 형식이 틀리면 유저가 원하는 목표를 직접 넣는다. 채점에는 `source = user`로 남는다.

### 하네스 (`baseline/harness.py`, `tools.py`)
- 온보딩 질문 한도는 5개다 (`MAX_QUESTIONS_ONBOARDING`).
- 온보딩 중에는 목표가 없다. `goal_progress` 도구는 `no_data`를 돌려준다.
- 목표 생성 뒤에는 만든 목표로 세계를 다시 만든다. 기존 `_same_past` 검사를 그대로 통과한다.
  - 유저 이해 이벤트에 만든 목표와 고친 칸을 넘긴다.
  - 실행 기록에 `goal`·`goal_source`·`goal_edits`를 남긴다.
- 보고서·목표안의 숫자도 숫자 검증에 넣는다 (`report_texts`). 월 이름·마감일 같은 글자는 검사하지 않는다.
- 새 도구 `flow_summary`
  - 달마다 앱 타입(수입·지출·이체)별 합계와, 수입·이체 행의 내용별 합계를 보여 준다.
  - 이중 집계가 섞인 그대로 주고, 걸러 내는 것은 에이전트 몫으로 둔다. 지출 요약만으로는 수입과 이체(월세·적금·카드대금)를 볼 수 없었다.

### 보고서·목표안 형식 (피드백 JSON, 온보딩에만)
```json
"report": {"months": [{"month": "2026-09", "income": 0, "spending": 0, "leftover": 0}], "monthly_leftover": 0,
           "categories": [{"category": "식비", "monthly": 0}], "patterns": ["주말 저녁 배달이 잦다"],
           "required_cut": 0, "summary": "한 줄"},
"goal_proposal": {"name": "일본 여행 (2주)", "amount": 2100000, "deadline": "2027-04-30",
                  "current_saved": 800000, "monthly_required": 260000}
```
- `required_cut` = 필요 월 저축액 − 월 남는 돈 (0 이상).
- 화면(C)과 계약(`contracts.py`) 후보다. 계약 파일은 혼자 바꾸지 않았다.

### 채점 (`baseline/score.py`)
- **report**
  - 월 남는 돈을 정답과 비교한다. 할부 기준 두 가지 중 가까운 쪽과 견준다.
  - 오차가 월 평균 수입의 10% 안이면 통과다.
- **goal**: 목표안을 냈는지, 출처(agent·user), 고친 칸, 목표 질문(goal·goal_flex)을 했는지, 만든 목표와 원하는 목표의 필요 월 저축액을 남긴다.
- **achievement**
  - 만든 목표 기준으로 끝난 달의 부족분(필요 − 진척, 기댓값)을 ②와 ③에서 비교해 메운 비율을 낸다. 기간 끝 목표 궤도도 같이 낸다.
  - 목표 조정으로 필요액이 줄어든 것도 반영된다.
- 목표가 없던 예전 실행 기록은 원하는 목표로 다시 채점한다.

### 싱글 에이전트 (`baseline/single.py`)
- 온보딩 프롬프트에 순서를 넣었다: 남는 돈 계산 규칙 → 목표 대화 → `forecast_goal` → 줄여야 할 금액 → 보고서·목표안.
- 만든 목표는 메모리 '목표'에 남는다.

### Swarm (`agent/swarm.py`, `memory.py`, A 영역)
- **온보딩 흐름**
  1. analyst: 확인 질문
  2. counselor: 목표 대화
  3. strategist: `set_report` → `propose_goal` → `propose_action`
  4. reviewer: `check_goal`
  5. counselor: 전달
- **코드 관문**
  - 보고서 숫자는 이번 도구 결과에 있어야 한다.
  - 목표안의 필요 월 저축액·줄여야 할 금액은 코드가 `forecast_goal`·`calculate`로 계산한다.
  - 목표안을 리뷰 전에 보낼 수 없다. `check_goal` 없이는 통과시킬 수 없다.
  - 남는 돈을 다시 올리면 목표안·리뷰를 다시 받는다.
- 주간 흐름과 기존 테스트 26개는 그대로 통과한다. 홉 한도(8)도 그대로다. 온보딩 흐름은 홉 4번이다.
- 만든 목표는 모든 역할의 메모리 뷰에 들어간다.

## 확인한 것
- `uv run pytest`: 335개 중 334개 통과.
  - 실패 1개는 공유 DB 비교(live)다. P1 평가 케이스가 14개에서 15개로 늘어서 DB를 다시 올려야 한다.
  - 원래 데이터 해시는 5명 모두 그대로다.
- 가짜 LLM 시나리오 (P1, 1/31까지, 싱글)
  - 좋은 정책: 목표 질문 G1 → 목표안 그대로 생성. 보고서 오차 1원으로 통과, 부족분 메운 비율 1.0.
  - 나쁜 정책: 목표안 없음 → 유저가 원하는 목표를 직접 입력, 메운 비율 0.0.
- dry 실행: 5명 × 싱글·Swarm 모두 끝까지 돈다.
- A 리포트(1700)의 "중복 수락이 효과에 겹쳐 반영되는지"
  - 같은 날 같은 제안이 두 번 수락돼도 효과는 한 번이다. P1에서 같은 날 두 번 넣어도 기댓값 75,771원으로 같았다.
  - 며칠 뒤 다시 수락되면 유지 기간만 그날부터 새로 센다 (10 §4 설계대로). 배율이 겹치지는 않는다.

## 확인 안 한 것 / 가정
- 원하는 목표의 금액·시점과 바꿀 수 있는 범위는 데모 값이다 (P3 2028년 말, P1 210만 원 포함).
- 보고서 통과 기준(월 수입의 10%)은 임시값이다.
- 실제 LLM이 5개 한도 안에서 목표 대화까지 하는지, Swarm이 이 순서로 흘러가는지는 실제 모델로 돌려 봐야 안다.
- P3는 평가 기간(12~1월)에 연말 경조사와 1월 PT 재등록이 몰려, 좋은 목표안이어도 기간 끝 목표 궤도에는 못 들 수 있다. 비교는 메운 비율로 본다.
